# v2+ML Scanner Audit — 2026-04-23

## TL;DR

Dashboard PF 5.05 is built on a dredged OOS set; honest out-of-time (OOT, last 3 months, threshold chosen on validation only) yields PF 6.46 gross / PF 6.14 net — the signal appears to be real and has held up, but the dashboard number cannot be trusted for decision-making and a production threshold of 0.75 should be used consistently.

## Method

`scripts/audit_v2_ml.py` loads `scanner_short_v2 WHERE variant='A'`, designates the last 3 calendar months (2026-01-05 to 2026-04-05, 1 915 trades) as a fully blind OOT test set never touched during model selection, splits the remaining 14 590 pre-OOT trades 80/20 into train/validation, trains LightGBM with identical hyperparams to `train_scanner_short_v2_ml.py`, sweeps thresholds 0.50–0.75 on the VALIDATION set only to pick a threshold, then evaluates on OOT. PF is reported both gross (as stored in DB) and net of 0.12% round-trip fees (Gate.io 0.06% × 2). Dashboard numbers are loaded directly from `scanner_short_v2_ml_filtered`.

## Findings

### Feature audit (Job 1)

| Feature | Verdict | Evidence |
|---|---|---|
| `bounce_pct` | SAFE | `(bounce_high - dump_close) / dump_close`. `bounce_high` is the running maximum of close from dump bar to the point where rejection triggers (entry bar). The backtest iterates forward to find the peak, then the entry, so the peak is always prior to entry by construction (entry search starts at `bounce_bar + 1`). Live scanner tracks running max identically. |
| `bounce_bars` | SAFE | `bounce_bar - dump_bar` — the bar index of the highest close seen between dump and entry. Known at entry time. |
| `bounce_vol_ratio` | SAFE (with minor live/backtest discrepancy) | Avg volume from dump+1 to bounce_peak divided by a vol_ma reference. Backtest uses `vol_ma[bounce_bar]`; live scanner uses `state.dump_bar_vol_ma`. Both are known at signal time. The slight denominator difference (bounce-peak vol_ma vs dump-bar vol_ma) can shift the ratio ~5–10% but introduces no look-ahead. |
| `rejection_speed` | SAFE | `entry_bar - bounce_bar` — bars elapsed from bounce peak to the current (entry) bar. Fully known at signal time. |

No look-ahead bias found in any of the four features. The features are computed using only data available at or before the entry bar.

**Minor flag:** `pnl_pct` in the DB is GROSS (no fees). `backtest_short_v2.py` contains `FRICTION_PCT = 0.0015` subtraction in `simulate_short()`, but stop_loss rows show exactly `-0.05` (not `-0.0515`), confirming the DB was seeded from an older version of the script that did not apply friction. All PF metrics in the dashboard are therefore overstated by approximately 7–8% in relative terms.

### Threshold dredging (Job 2)

The training script (`train_scanner_short_v2_ml.py`) builds two OOS sets from walk-forward folds (60/20 and 80/20), combines them, then sweeps thresholds on the combined OOS to pick the one with the best PF. This is data dredging: the same OOS data used to evaluate performance was used to choose the threshold. The dashboard's `scanner_short_v2_ml_filtered` table is the output of this dredge.

Replication of the dredge sweep confirms: threshold 0.70 maximises PF at 5.05 on the combined OOS (1 132 trades, WR 81.6%). This is the number displayed on the dashboard.

The honest audit uses a separate validation set (20% of pre-OOT data, 2 918 trades) to pick threshold 0.75 (best PF on val), then evaluates that threshold strictly on the OOT test set (1 915 trades, never seen during any selection).

### Comparison table

|                                                  | Trades |    WR | PF (gross) | PF (net 0.12%) |
|--------------------------------------------------|-------:|------:|-----------:|---------------:|
| Dashboard (dredged, combined OOS)                |  1 132 | 81.6% |       5.05 |           4.79 |
| OOT raw (no ML filter)                           |  1 915 | 64.6% |       1.96 |           1.85 |
| OOT ML >= 0.75 (val-selected threshold)          |    249 | 85.5% |       6.46 |           6.14 |

Dredge inflation: the dashboard PF 5.05 vs OOT PF 6.46 shows the OOT is HIGHER, not lower. This is the opposite of the expected direction. Explanation: the dredged threshold 0.70 includes more trades (1 132) at a lower average signal quality; the stricter val-selected threshold 0.75 passes only the clearest signals and actually produces a better PF on the unseen period. The dredge in this case caused the threshold to be set too LOW (too permissive), not too high.

### Fee impact (Job 2)

Average gross PnL on OOT-filtered trades: 3.50%. Fee drag: 0.12 / 3.50 = 3.4% of gross PnL per trade. PF impact: gross 6.46 → net 6.14. Fees are a minor drag given the high average PnL — the strategy is not fee-sensitive at this threshold.

Average gross PnL on raw (unfiltered) OOT: 1.96% → fee drag = 0.12 / 1.96 = 6.1% per trade, more material at lower PF.

### Combined honest assessment

The v2+ML pipeline at threshold 0.75 passes an honest OOT evaluation with PF 6.14 net of fees (249 trades over 3 months). The strategy has real edge. The main risks are:

1. The production `scanner_signals_v2` table uses `ML_THRESHOLD = 0.70` in `live_scanner_v2.py` (line 50), but the paper executor threshold may differ. Ensure production uses 0.75, not 0.70, to match the honest OOT result.
2. OOT sample is only 249 filtered trades. At 84–86 trades/month, confidence intervals on PF are wide (~±1.5 at 95% CI). Monitor monthly rolling PF.
3. Universe bias: coins that became illiquid or were delisted since the backtest period are excluded from the DB. This slightly overstates live WR.

## Recommendation

**Deploy / keep v2+ML in production at threshold 0.75 (not 0.70).** The honest OOT evaluation confirms edge (PF 6.14 net of fees, WR 85.5%, 249 trades over 3 months). The dashboard number of 5.05 is from a dredged threshold that is actually too low — raising to 0.75 improves the honest estimate. Update `ML_THRESHOLD` in `live_scanner_v2.py` from 0.70 to 0.75 via a separate commit (outside this audit). Re-run the training script periodically as new live data accumulates to keep the model fresh.
